# FutureQuest

Career-guidance platform for teenagers and young adults. A questionnaire feeds an LLM-generated
report covering career traits, strengths, suggested careers and next steps.

## Where things are documented

- **`docs/requirements.md`** — product requirements and the full stack, with the reasoning for
  each choice.
- **`docs/schema.md`** — the complete Postgres schema: ER diagram, DDL, and *why* each decision
  was made. This is the source of truth for the data model. Read it before changing anything
  database-shaped.
- **`docs/features.md`** — a running inventory of what exists, what's built but dormant, and
  what's deliberately absent. **Keep it current**: update it whenever a feature lands or a
  deferral changes, so "what can it do right now?" never needs a code read to answer.
- **`docs/design.md`** — interface conventions: tone, type, colour, components, interaction,
  and the data-visualisation rules. Read it before building a screen; update it when a
  convention changes.
- **`docs/plan.md`** — the plan for the next substantial piece of work. Currently payments and
  the entitlement gate. Delete or replace it when that lands; a stale plan is worse than none.
- **`README.md`** — setup and day-to-day commands.

## Decisions that are easy to undo by accident

These are all argued out in `docs/schema.md`; repeated here because each one looks like a
simplification until you know why it isn't.

- **Alembic migrations are hand-written, never autogenerated.** Autogenerate cannot see triggers,
  plpgsql functions, functional indexes or CHECK constraints — which is most of this schema's
  integrity. Use it to scaffold, then write the SQL.
- **No test may read ambient configuration.** `.env` is a developer's demo setup — the paywall
  bypass on, Google credentials present, a real session secret — and a test that inherits any
  of it passes on one machine and fails on another. Every setting a test depends on is forced
  in `conftest.py`, by an autouse fixture for the default state and an opt-in fixture for the
  exception. This has already caught three times; add the fixture when you add the setting.
- **Tests run against real Postgres, never SQLite.** The schema uses enums, arrays, GIN indexes,
  plpgsql triggers and deferrable constraints. SQLite has none of them, so tests that avoid
  Postgres test almost nothing.
- **A published questionnaire is immutable — row, questions and options.** Changes mean a new
  version via `fork_questionnaire()`. Enforced by triggers. The admin UI affordance is "create a
  new draft version", never "edit".
- **Pay figures come from the `career_pay` lookup, never from the model.** A lookup miss omits the
  figure; it never fabricates one. `payload.careers[].pay` is therefore optional and the UI must
  render without it.
- **Paid reports are generated server-side only after the entitlement gate query returns a row.**
  Never generate and hide client-side.
- **Payment unlocks the questionnaire; it does not produce a report.** A report is scored from
  the answers, so a full report cannot exist until the paid sections have been answered. Any
  flow that waits for one after a purchase waits forever.
- **A section can only be submitted once, and the client has to be told which are done.**
  `QuestionnaireOut.completed_sections` carries that, from the completion timestamps already on
  the response row. Without it the client loops over every available section, resubmits the
  free one, and is refused with a 422 — which is exactly what happens to a visitor who pays
  after finishing the free tier.
- **The entitlement gate is asked once per request, and every answer is derived from that one
  row.** Which sections may be answered, and what tier the report is, come from the same
  question. Two queries could disagree — the second might see an entitlement that has just
  been revoked — and the visitor would be allowed to answer a section and handed a report that
  says it wasn't paid for.
- **Two kinds of access, and they are not interchangeable.** A *capability* (ownership cookie)
  says this browser started these responses. An *identity* (sign-in session) says this browser
  belongs to this user. Only the second grants account-level access, and it is only ever
  issued after Google asserts `email_verified` — because the capture email is unverified and
  `_find_or_create_user` reuses an account by email, so a session minted from the capture form
  would be account takeover by guessing an address. `app/access.py` holds the combined rule;
  don't re-derive it at a call site.
- **An origin is selected from `ALLOWED_ORIGINS`, never read out of a header.** `app/origins.py`
  uses `X-Forwarded-Host`, `Origin`, `Referer` and `Host` only to *choose* a configured entry,
  falling back to the first. Using one directly would let a forged header redirect sign-in — and
  the authorization code with it — to an attacker's host. Relatedly, the Vite proxy must not set
  `changeOrigin`: it rewrites `Host` to the backend's own address, leaving nothing to match.
- **Unowned resources return 404, never 403.** A 403 confirms the id exists, which is the one
  thing an attacker enumerating UUIDs is trying to learn. The body must match the genuine
  not-found body too.
- **Entitlements are enforced server-side.** The gate checks `entitlements` table, not a
  deployment flag.
- **Refunds must stamp `revoked_at` on entitlements.** `purchases.refunded_at` alone does not
  revoke access — the gate reads `entitlements`.
- **Background jobs belong on a Postgres-backed queue — which is not built yet.** The reason it
  has to be Postgres rather than Redis is that a job must be enqueueable in the same transaction
  as the purchase that requires it, so there's no window where someone has paid and the job was
  lost. Today the only background work is report email, running on FastAPI `BackgroundTasks` and
  explicitly *not* durable (see the header of `app/email.py`). Build the queue before anything
  where losing a job costs money, and don't swap in Redis without accounting for the above.

## Conventions

- Python: `uv`, run commands as `uv run <cmd>` from `backend/`. Lint and format with `ruff`.
- Frontend: `pnpm`.
- Secrets are `SecretStr` in settings; call `.get_secret_value()` at the point of use.
- Frontend tests: `frontend/scripts/test.sh` — Node's built-in test runner, with `rolldown`
  transpiling the TypeScript first. No test framework is installed, deliberately.

## Entitlement Gate

The entitlement gate (`app/entitlements.py`) checks whether a user has active paid access
to a response. It supports two models:

- `single_report`: Tied to a specific response. No expiry — reading the report doesn't
  consume it, so a bought report stays readable until it's refunded.
- `window`: Not tied to a response, valid for a time window

The gate query is in `app/entitlements.py` and is used by `app/routes/public.py` to
gate access to paid sections. It checks `revoked_at IS NULL` and the `valid_from`/
`valid_until` window — **not** `consumed_at`, which nothing sets and which exists for the
`coaching_session` kind alone. A `coaching_session` is a booking, not report access, and
is excluded from the query: since such rows name no response, counting them would unlock
*every* report the user has.

**The entitlement gate is enforced server-side.** The gate checks `entitlements` table,
not a deployment flag.

**The gate asks about the response's owner, not the caller.** The entitlement is looked up by
`user_id`, so a visitor holding only the ownership cookie would look entitled to nobody.
Every route that gates therefore reads `questionnaire_responses.user_id` and asks the gate
about *that* — and a `single_report` names one response, so the response id is part of the
question too. A preview with no response to ask about (`GET /api/questionnaire` without
`?response_id=`) therefore serves only the free tier, even for a visitor who has paid for a
specific response.

**The report tier follows the gate.** `app/routes/public.py` asks the gate **once** and
derives both the sections and the tier (`ReportTier.FULL` vs `ReportTier.FREE`) from that one
answer, because two queries could disagree — a second one a moment later might see an
entitlement that has just been revoked — and then the visitor would be allowed to answer a
paid section and be handed a report that says it wasn't paid for.

## Payments

Three modules, each with one job:

- **`app/stripe_client.py`** owns the SDK: the client, `PaymentsNotConfiguredError`, the Price
  id, the display price and the checkout metadata. The only other module that imports
  `stripe` is the webhook route, which needs `stripe.Webhook.construct_event` — a
  module-level static method that takes no client.
- **`app/payments.py`** owns the writes: `grant_purchase`, `revoke_for_refund`. Both are
  called by the webhook *and* by the browser-return path, so "a completed checkout becomes
  access" is written once.
- **`app/routes/payments.py`** owns the routes: `GET /api/pricing`,
  `POST /api/responses/{id}/checkout`, `POST /api/stripe/webhook`,
  `GET /api/checkout/{session_id}`.

**Rules that are easy to undo by accident:**

- **The webhook verifies the exact raw signed body before parsing it.** `await
  request.body()` gives the bytes Stripe signed; re-serialising parsed JSON would change them
  and break the signature.
- **Stripe's Price id is authoritative for charging; the configured display price must match
  it.** `report_price_cents` is what the paywall shows, `stripe_price_id` is what's charged.
  A mismatch is a display bug, and the rollout checklist checks them against each other.
- **The entitlement goes to the response's current owner**, not to the checkout metadata's
  copy of the user id. Sign-in re-points a response at a verified account, so the owner can
  change between checkout and delivery. The metadata's user id is a cross-check.
- **Idempotency comes from the database, not from a check.** `INSERT ... ON CONFLICT
  (stripe_checkout_session_id) DO NOTHING`. A read-then-write pre-check is a race, and Stripe
  retries deliveries for up to three days.
- **`purchases.paid_at` is when the money arrived**, taken from the Stripe event's timestamp.
  For a delayed payment method that can be days after `checkout.created`.
- **A Stripe Checkout Session ID is not authority to view a response.** It appears in a URL,
  and URLs get shared. The return path checks `may_access_response` for the response the
  session names.
- **Refunds must stamp `revoked_at` on entitlements.** `purchases.refunded_at` alone does not
  revoke access — the gate reads `entitlements`.
- **Webhook status codes are chosen for Stripe's behaviour.** 400 for a body that isn't a
  valid signed event (a forged body will never become good, and 400 stops the retries), 503
  when the secret isn't configured, 200 for everything else — including event types we
  ignore, because Stripe retries any non-2xx.
- **The Stripe SDK's objects are not dicts.** `checkout.metadata` is a `StripeObject` and
  `.get()` on it raises. Use `metadata_value()` in `app/payments.py`, which also handles
  missing or non-mapping metadata.
- **A *missing* SDK field is worse than a wrong one.** `checkout.metadata` raises
  `AttributeError` for the attribute itself when a session has no metadata at all, so
  `stripe_field()` reads it defensively. A missing field means a malformed event (400); an
  event of an unhandled *type* is well-formed and is acknowledged and ignored (200). Both
  stop Stripe retrying, and they mean different things.
- **Checkout URLs are built from `ALLOWED_ORIGINS`**, through `app/origins.py` — never from a
  header and never hard-coded.
- **Optional integrations stay optional.** With no Stripe keys the app starts, the gate still
  works, and the routes that need Stripe return 503 naming the missing setting.
- **The webhook and the browser return share one grant implementation.** `grant_purchase()`
  is called by both, so the two can't disagree about what a purchase buys. A visitor who
  has just paid must not be refused because a webhook delivery was slow.
- **The Stripe seam has its own test suite.** `backend/tests/test_stripe.py` covers the SDK's
  object shapes, the raw-body signature check, idempotency, refunds and the return path. The
  outbound call is faked; the inbound webhook is exercised with real signed event bodies.
  `backend/tests/test_payments.py` covers the product consequences. The frontend's payment
  calls are covered in `frontend/src/api/client.test.ts`.

## API reference

FastAPI generates it: `/docs`, `/redoc`, `/openapi.json` with the server running. Don't write a
parallel prose copy — it drifts. If something about the contract isn't visible there, fix the
schema rather than document around it (as was done for the report payload, which was an opaque
`dict[str, Any]` until `ReportPayloadOut` gave it a shape).

## Frontend layering

Four layers, strictly ordered — `src/pages` and `src/components` (views) → `src/api/queries.ts`
and `src/store` (controllers) → `src/api/client.ts` and `src/api/types.ts` (the API layer) →
the backend.

**Nothing outside `src/api/` may call `fetch`, or know a URL or status code.** That's what keeps
the contract in one module, so a backend change breaks one file rather than six components.
`src/api/types.ts` is a hand-written mirror of `app/schemas.py` and can drift; generating it
from `/openapi.json` with `openapi-typescript` is the standing upgrade.
