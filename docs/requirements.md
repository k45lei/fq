# Context

FutureQuest is a platform that provides teenagers and young adults a service that helps them to decide a career path. It does so by gathering information about the users through a questionnaire, and then compiling those results to give them some direction on career paths.

# Flow

## Details

The flow starts with capturing the user's basic information such as names, email, and optionally school.

Then, the user proceeds with filling out the questionnaire that gathers enough information to provide them with helpful insight.

After users complete the questionnaire, they are given a composite report that tells them their career traits (enterprising, creative, realistic, conventional, social, investigative), career strengths (skills and traits), and a few career suggestions that use the career traits and strengths as explanation to why the career might be a good fit. Some additional information is provided such as:

- 5 to 7 potential challenges and what to be mindful of
- Ranking of fitting career families containing suggeested careers within each
- Next steps to take (projects, topics to learn, etc.)

The user should also receive an email copy of the results summary after completing the questionnaire.

# Stack

## Business, Administrative, and Others

Stripe (payments; source of truth for money and SKUs)
Resend (transactional email — results summary)

## Frontend

React + TypeScript
Vite (build)
pnpm (package manager)
React Router (routing)
TanStack Query (server state: report history, polling a queued report to completion)
Zustand + persist middleware (questionnaire state; this is the localStorage session-recovery mechanism)
Tailwind + shadcn/ui (styling)
Jinja (email templates, rendered server-side — see note below)

## Backend

Python
FastAPI (web framework)
SQLAlchemy 2.0 (typed) + asyncpg (database access)
Postgres
 - Alembic for migrations, **hand-written, not autogenerated** — the schema relies on triggers,
   plpgsql functions, functional indexes and CHECK constraints that autogenerate can't see
Postgres-backed job queue (procrastinate / pgqueuer) for report generation — **not built yet**
 - lets the job be enqueued in the same transaction as the purchase, so there's no window where
   a user has paid and the job was lost
 - adds no infrastructure: it's the database we already run
 - today's only background work is report email, on FastAPI `BackgroundTasks` and not durable.
   The queue is a prerequisite for payments, where a lost job has a cost attached
Authlib (Google OAuth flow + ID token verification), with FastAPI dependencies enforcing access
Pydantic v2 + pydantic-settings (validation, config; also guards the `reports.payload` shape)
WeasyPrint (server-side PDF, rendered from a Jinja template in the worker)
uv (packaging and lockfile)

Email templates are Jinja, not React Email as originally planned. React Email is a Node
toolchain and sending happens in Python — using it would mean authoring templates in the
frontend, exporting HTML, and shipping it to the backend to fill in. Jinja keeps email
rendering server-side and in the same place as the PDF.

Not Django: its ORM can't model composite foreign keys, which the schema depends on throughout.
The Django admin looks like a shortcut to the admin pages and isn't.

## Infrastructure

Deferred, with one exception: **local Postgres in Docker from day one.** The schema uses enums,
arrays, GIN indexes, plpgsql triggers and deferrable constraints, none of which SQLite has, so
tests have to run against real Postgres or they test almost nothing.

Deferred: hosting (Fly / Render, containerized — WeasyPrint needs cairo/pango system libraries),
managed Postgres, frontend CDN, Sentry, PostHog, CI.

Rationale for deferring: infrastructure choices are reversible, code-shape choices aren't.

# Functional requirements

- Result history (session recovery? if only needing session recovery, using localstorage might be an option)
- Save results as PDF
- User database (using information gathered from basic information)
- Google oAuth for SSO
- Somewhat consistent results (multiple identical assessment inputs should result in similar reccomendation outputs)
- Session recovery (questionnaire inputs should be saved as the user completes them, allowing for smooth continuation in case they can't finish in one shot)
- 3 sections the questionnaire should comprise of: career interests, career strengths, EQ assessment
	* The final results should take the input of all 3 sections into consideration
	* The final result should associated a 'fit score' to provide an idea to users of how much of a fit they would be for a particular career path
	* for the final product, the interests section is the only free section. For free users, they should be able to complete the career interests section to get their results. Then, users are prompted with a paywall that lets them complete the latter 2 sections for a more accurate and personalized report.
